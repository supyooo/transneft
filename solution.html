0. Предметная область простыми словами

Как устроен нефтепровод

Нефть по трубе сама не течёт: её толкают насосы, а на трение о стенки уходит давление. Поэтому труба разбита на куски, и в начале каждого стоит насосная станция, которая снова поднимает давление.

 РП  ──► ГНПС ══КП══КП══КП══► НПС ══КП══КП══КП══► НПС ══КП══КП══► РП
 │       (старт)   линейная часть   (подкачка)                        │
 └──────────────────── технологический участок (ТУ) ───────────────────┘
          перекачка «из резервуара в резервуар»
ТерминЧто это на самом деле
МН / МТМагистральный нефтепровод / трубопровод: вся труба из точки А в точку Б, сотни и тысячи километров
ТУТехнологический участок: кусок МН, который гидравлически работает как одно целое, от резервуарного парка до следующего парка. Все НПС внутри ТУ управляются согласованно
РПРезервуарный парк, группа больших резервуаров (РВС). Буфер между ТУ, позволяет участкам работать независимо
ГНПСГоловная станция ТУ. Забирает нефть из РП. Кроме обычного состава НПС имеет ПНС (подпорную насосную): магистральные насосы не могут сами вытянуть нефть из резервуара, нужен подпор
НПСПромежуточная станция через 50–100 км, поднимает давление
ЛЧЛинейная часть, сама труба между станциями
КП на ЛЧЧерез 10–30 км: линейная задвижка, которой можно отсечь кусок трубы при аварии, и датчики давления до и после неё. На практике это контролируемый пункт телемеханики, поэтому на мнемосхеме у КП ещё есть U (напряжение питания) и U_СКЗ / I_СКЗ (станция катодной защиты трубы от коррозии)
КП в конце ТУКонечный пункт с РП. В задании одна аббревиатура используется в двух смыслах, в модели это разные типы

Что внутри промежуточной НПС (рис. 2 задания)

Нефть проходит по станции так: вход → КПП СОД → ФГУ → НС → САРД → КПП СОД → выход.

№УзелЗачем
3КПП СОДКамера пуска-приёма средств очистки и диагностики. По трубе гоняют «поршни»: скребки чистят стенки, внутритрубные дефектоскопы ищут дефекты. Камера приёма их ловит, камера пуска запускает дальше
4ФГУФильтры-грязеуловители, защищают насосы от мусора. Две параллельные нитки: одна работает, вторую можно чистить
1НСМагистральная насосная: 4 МНА последовательно, давление складывается. Обычно 3 в работе и 1 в резерве. Обратный клапан на обводе пропускает нефть мимо остановленного насоса
2САРДСистема автоматического регулирования давления: 2 регулирующие заслонки. Не дают давлению на выходе превысить допустимое для трубы, а на входе упасть ниже допустимого для насосов

Мнемосхема (рис. 3) — экран диспетчера

Это экран системы диспетчерского контроля и управления. Внизу обзорная схема, красной рамкой выделен наш участок. На нём читается:

  • Два параллельных ТУ в одном коридоре. ТУ-1: ГНПС-1 → КП 282…499 → НПС-2 → КП 6…114 → РП. ТУ-2: ГНПС-2 → КП 15…166 → НПС-2 → КП 214…416 → РП.
  • Общий РП нарисован между ГНПС-1 и ГНПС-2. Это ситуация из условия: «для каждого ТУ своя НПС, но РП может быть общий».
  • На ТУ-1 после НПС-2 нумерация км начинается заново (499 → 6). Километр не может быть ключом для упорядочивания.
  • Верхняя часть экрана — детализация фрагмента ТУ-2 (КП-99…КП-166) и узел входа НПС-2 с камерами СОД.

Задание 1

Структура хранения информации об участке МН

1.1. Анализ исходных данных

ТУТехнологическая цепочкаКП
ТУ-1Общий РП → ГНПС-1 → КП-282 … КП-499 → НПС-2 → КП-6 … КП-114 → РП16 + 10
ТУ-2Общий РП → ГНПС-2 → КП-15 … КП-166 → НПС-2 → КП-214 … КП-416 → РП13 + 15

Почему одного parent_id недостаточно:

  1. Общий РП входит в состав и ГНПС-1, и ГНПС-2, а в дереве у объекта только один родитель.
  2. Положение «до / после по трубе» — это порядок по ходу потока, а не вложенность. Деревом он не описывается.
  3. Километраж не уникален и не монотонен: 499 → 6 на ТУ-1, у ТУ-1 и ТУ-2 разные шкалы.

1.2. Проектное решение: дерево состава и граф связей

ИзмерениеСпособ храненияОтвечает на вопрос
Составobject.parent_id, строгое дерево, ровно один родительКто родитель, кто дочерний; из чего состоит объект
Технологические связиТаблица object_link с типом связиЧто выше и ниже по потоку; кто использует общий объект; где объект размещён
  • FLOW — A → B по ходу потока нефти.
  • USES — A использует разделяемый объект B, не являясь его родителем (обе ГНПС → общий РП).
  • LOCATED_AT — A размещён на технологической площадке B.

Общий РП в дереве принадлежит объекту «Технологическая площадка» (на практике это ЛПДС), а обе ГНПС ссылаются на него связью USES. Дерево остаётся деревом, а совместное использование выражено явно.

Связь с PI AF. Тот же принцип есть в PI AF: у элемента одна связь Composition (Parent-Child) и сколько угодно Weak reference. Поэтому модель без потерь сопоставляется с исходной ИМ из задания 2.

Дополнительно в модели:

  • Справочник типов и правила композиции (object_type, object_type_rule): НС — ровно 4 МНА, ПНС — от 1 до 10 ПА, КП — задвижка и 2 датчика давления. Задвижку нельзя положить прямо в РП.
  • Параметры (parameter): сигналы с временными рядами. Поля object_id, parameter_id, label, nic — это «БД метаданных» задания 2.
  • Версионность (valid_from, valid_to): оборудование меняют, и история должна ссылаться на состав на момент измерения.
  • Порядок seq_no по ходу потока; километр km — атрибут, а не ключ.

ОбъектСостав

Связи FLOW задают цепочку каждого ТУ: общий РП → ГНПС → КП … → НПС-2 → КП … → РП конечного пункта. Внутри станции: ПНС → ФГУ → НС → САРД → КПП СОД (ГНПС) и КПП СОД → ФГУ → НС → САРД (НПС). Внутри НС: МНА-1 → МНА-2 → МНА-3 → МНА-4.

1.6. Как определить положение объекта

Модель загружена в тестовую БД, запросы выполнены на ней.

ВопросСпособРезультат
Родители датчика «до задвижки» на КП-116Подъём по parent_idДД → КП-116 → ЛУ ГНПС-2 – НПС-2 → ТУ-2 → МТ
Состав ТУ-2Спуск по parent_id215 объектов
Кто использует общий РПobject_link, тип USESГНПС-1, ГНПС-2
Что ниже по потоку от КП-387 (ТУ-1)Обход связей FLOWКП-390 … КП-499 → НПС-2 → КП-6 … КП-114 → РП
WITH RECURSIVE up AS (
    SELECT object_id, parent_id, name, type_code, 0 AS lvl
    FROM object WHERE object_code = 'MT1.TU2.LU1.KP116.DD_BEFORE'
    UNION ALL
    SELECT o.object_id, o.parent_id, o.name, o.type_code, u.lvl + 1
    FROM object o JOIN up u ON o.object_id = u.parent_id
)
SELECT lvl, type_code, name FROM up ORDER BY lvl;

1.7. Допущения

Проговорите на собеседовании. Количество задвижек в узле КПП СОД, подпорных агрегатов и резервуаров взято условно: в реальности оно берётся из технологических схем и паспортов объектов.

  • Подключение стороннего трубопровода к ТУ-1 в районе 390 км лежит за пределами участка; в модели оно описывается связью FLOW от объекта другого МН.
  • СКЗ, датчики температуры, СИКН и другое оборудование добавляются новыми типами и правилами, без изменения структуры.

Задание 2

ТЗ на сервис переноса данных временных рядов

Суть задачи

Сейчас модель (дерево «ТУ → НПС → МНА → атрибут "Давление на выходе"») хранится в PI AF. У каждого атрибута есть label (имя или путь) и NIC (идентификатор сигнала). Сами значения во времени лежат в MS SQL с ключом NIC.

Целевой стек: новая модель в PostgreSQL (та самая из задания 1, у параметров есть object_id, parameter_id и для сопоставления label, nic) и история в ClickHouse с ключом (object_id, parameter_id).

Сервис переносит всю историю и переписывает ключ со старого NIC на новый (object_id, parameter_id). Связку даёт PostgreSQL, а PI AF используется для сверки, что сопоставление верное.

1. Общие сведения и цели

НаименованиеСервис переноса исторических данных временных рядов
ОснованиеРаботы по созданию единого хранилища данных (ЕХД)
ТипСерверное приложение (Java 17+ или Python 3.11+) в контейнере
РежимОднократный полный перенос и инкрементальная досинхронизация до переключения потребителей
  1. Перенести 100 % истории сопоставленных параметров без потерь и искажений.
  2. Перевести идентификацию с NIC на (object_id, parameter_id).
  3. Формировать отчёт о сверке источника и приёмника по каждому прогону.
  4. Не влиять на работу производственных систем-источников.

2. Источники и приёмники

СистемаРольДоступДанные
PI AFИсточник ИМ для сверкиPI OLEDB Enterprise, только чтениеlabel, NIC
MS SQLИсточник временных рядовTDS (ODBC/JDBC), только чтение, лучше репликаNIC, timestamp, value, quality
PostgreSQLЦелевая ИМ и служебные таблицыSQLobject_id, parameter_id, label, nic
ClickHouseПриёмник временных рядовHTTP / Native, записьobject_id, parameter_id, ts, value, quality

Вопросы к заказчику. Структура таблиц истории в MS SQL; время в источнике локальное или UTC; справочник кодов качества; объём (число NIC, глубина истории, частота записи); есть ли реплика для чтения; менялся ли NIC у параметров за период истории.

3. Функциональные требования

ФТ-1. Загрузка маппинга

Сервис читает из PostgreSQL object_id, parameter_id, label, nic, data_type, unit. Перечень можно ограничить фильтром (по ТУ, типу объекта, списку параметров) для пилота.

ФТ-2. Сверка с PI AF

Сервис выгружает из PI AF пары label ↔ NIC и сравнивает с PostgreSQL. В отчёт попадают: label не найден в PI AF; NIC различается; сигнал PI AF не покрыт маппингом; один NIC у нескольких параметров. Такие параметры не переносятся (статус MAPPING_ERROR), пока маппинг не исправят.

ФТ-3. Формирование заданий

Работа делится на задания «параметр × месяц». Границы истории каждого NIC определяются через MIN/MAX(timestamp). Задания и статусы хранятся в PostgreSQL, поэтому после сбоя работа продолжается с места остановки.

ФТ-4. Извлечение из MS SQL

Чтение пачками по 100 000 строк с keyset-пагинацией по (nic, timestamp), без OFFSET. Нужен индекс по (nic, timestamp). Режим snapshot isolation или чтение с реплики, без блокировок производственных таблиц.

ФТ-5. Преобразование

ЭлементПравило
КлючNIC → (object_id, parameter_id)
ВремяПриведение к UTC. Пересчёт по базе часовых поясов, а не фиксированным смещением: в России было летнее время до 2011 года, а Москва жила по UTC+4 в 2011–2014 годах
ЗначениеЧисловые → Float64; дискретные (состояние задвижки, агрегата) → код по справочнику; строковые → отдельное поле
КачествоКоды источника, в том числе состояния PI (Bad Input, I/O Timeout, Shutdown), приводятся к справочнику ЕХД. Недостоверные значения переносятся с признаком
ЕдиницыПри расхождении (например, кгс/см² → МПа) — пересчёт по справочнику с фиксацией правила
АномалииNaN, NULL, дубли, выход за диапазон переносятся как есть с признаком. Очистка — задача отдельного контура качества

ФТ-6. Запись в ClickHouse

Вставка пачками не меньше 10 000 строк (лучше от 100 000): мелкие вставки вызывают ошибку «too many parts».

CREATE TABLE ts_history
(
    object_id     UInt64,
    parameter_id  UInt64,
    ts            DateTime64(3, 'UTC'),
    value         Float64,
    value_str     Nullable(String),
    quality       UInt16,
    source        LowCardinality(String),   -- 'MSSQL_LEGACY'
    load_id       UInt64,                   -- ID прогона
    inserted_at   DateTime DEFAULT now()
)
ENGINE = ReplacingMergeTree(inserted_at)
PARTITION BY toYYYYMM(ts)
ORDER BY (parameter_id, ts);

ReplacingMergeTree делает запись идемпотентной: повторная загрузка периода после сбоя не создаёт дублей.

ФТ-7. Режимы запуска

РежимНазначение
fullПолный перенос всей истории
incrementalПеренос с отметки последнего прогона до текущего момента, чтобы не было разрыва перед переключением
reloadПерезагрузка периода или параметров после исправления маппинга
verifyТолько сверка

ФТ-8. Сверка результата

По каждому заданию сравниваются число записей, MIN/MAX времени, SUM и AVG значений, распределение по кодам качества. Задание выполнено, только если сверка прошла. По итогам — отчёт: перенесено полностью, с расхождениями, не перенесено и почему.

ФТ-9. Управление и мониторинг

Запуск, пауза и останов через CLI или REST API. Прогресс (доля заданий, строк в секунду, оценка окончания) — в логах и метриках Prometheus.

4. Алгоритм работы

  1. Загрузить маппинг из PostgreSQL.
  2. Выгрузить ИМ из PI AF, сверить маппинг, сохранить отчёт расхождений.
  3. Определить границы истории каждого NIC в MS SQL.
  4. Создать задания «параметр × месяц».
  5. Для каждого задания в N потоков: прочитать пачку → преобразовать → записать в ClickHouse → сохранить чекпоинт. Повторять до конца периода.
  6. Посчитать контрольные агрегаты в обеих СУБД, сравнить, выставить статус DONE или VERIFY_FAILED.
  7. Сформировать итоговый отчёт прогона.

6. Служебные таблицы (PostgreSQL)

CREATE TABLE mig_run (
    run_id        bigserial PRIMARY KEY,
    mode          varchar(20) NOT NULL,     -- full / incremental / reload / verify
    started_at    timestamptz NOT NULL DEFAULT now(),
    finished_at   timestamptz,
    status        varchar(20) NOT NULL,     -- RUNNING / DONE / FAILED / STOPPED
    config        jsonb                     -- снимок параметров запуска
);

CREATE TABLE mig_task (
    task_id       bigserial PRIMARY KEY,
    run_id        bigint REFERENCES mig_run,
    parameter_id  bigint NOT NULL,
    nic           varchar(100) NOT NULL,
    period_from   timestamptz NOT NULL,
    period_to     timestamptz NOT NULL,
    status        varchar(20) NOT NULL,     -- NEW / IN_PROGRESS / LOADED / DONE /
                                            -- VERIFY_FAILED / FAILED / MAPPING_ERROR
    last_ts       timestamptz,              -- чекпоинт
    rows_read     bigint DEFAULT 0,
    rows_written  bigint DEFAULT 0,
    src_checksum  jsonb,                    -- count/min/max/sum источника
    dst_checksum  jsonb,                    -- то же для приёмника
    attempts      int DEFAULT 0,
    error_text    text,
    updated_at    timestamptz DEFAULT now(),
    UNIQUE (parameter_id, period_from, period_to, run_id)
);

CREATE TABLE mig_mapping_issue (
    run_id        bigint REFERENCES mig_run,
    parameter_id  bigint,
    label         varchar(300),
    nic_pg        varchar(100),
    nic_af        varchar(100),
    issue_type    varchar(30)  -- LABEL_NOT_FOUND / NIC_MISMATCH / NOT_MAPPED / DUPLICATE
);

7. Порядок контроля и приёмки

№ПроверкаКритерий успеха
1Пилот на одном ТУСверка 100 % заданий без расхождений; замерена скорость, уточнён план

6Нагрузка на источникПоказатели MS SQL в согласованных пределах

8. Риски и допущения

  • Время. Часовые пояса и летнее время дают пропуски и дубли в пределах часа. Обязательна проверка на данных до 2014 года.
  • Маппинг во времени. Если датчик меняли и NIC сменился, одному параметру соответствуют несколько NIC в разные периоды. Нужен маппинг с периодом действия.
  • Сжатие в источнике. Прореженная история переносится как есть, без интерполяции.
  • Объём. Оценка условна и уточняется на пилоте.

Что сказать на собеседовании

Задание 1. Одного parent_id недостаточно: общий РП ломает дерево, а положение по трассе — не иерархия. Поэтому дерево состава плюс типизированный граф связей, как composition и weak reference в PI AF. И километраж не ключ: после НПС-2 нумерация начинается заново.

Задание 2. Главное — доказуемая полнота: идемпотентная запись, чекпоинты, сверка count/min/max/sum по каждому параметру за каждый месяц. И не навредить источнику, это производственная система.

Связь заданий. Таблица parameter из задания 1 и есть «БД метаданных» object_id, parameter_id, label, nic из задания 2.
